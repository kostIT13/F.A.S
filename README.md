# FAS — FAISS + FastEmbed RAG-сервис

Векторный поисковый сервис с REST API для хранения коллекций текстовых точек и семантического поиска по ним.

**Стек:** Python 3.12 · FastAPI · FAISS (IndexFlat / IndexIDMap2) · FastEmbed (`bge-small-en-v1.5`) · SQLite (SQLAlchemy)

---

## Возможности

- Создание коллекций с фиксированной размерностью векторов и типом метрики (`cosine`, `dot`, `euclid`).
- Upsert точек: текст автоматически эмбеддится моделью, вектор кладётся в индекс FAISS, метаданные — в SQLite.
- Семантический поиск по текстовому запросу с возвратом id, score и payload.
- Удаление точек и целых коллекций.
- Перестроение индекса по метаданным (восстановление после сбоев).
- Кэш индексов в памяти (LRU) с проверкой согласованности с диском по `mtime`.

## Быстрый старт

### Способ 1: локально

Требуется **Python ≥ 3.12**.

```bash
# 1. Создать виртуальное окружение (рекомендуется)
python -m venv .venv

# 2. Активировать окружение
# Windows (cmd):
.venv\Scripts\activate
# Windows (PowerShell):
.venv\Scripts\Activate.ps1
# Linux/macOS:
source .venv/bin/activate

# 3. Установить зависимости
pip install uv
uv pip install -e .

# 4. Запустить сервер
uvicorn src.main:app --host 0.0.0.0 --port 8000
```

> **Важно:** при первом запуске FastEmbed скачает модель `BAAI/bge-small-en-v1.5` (~130 МБ). Требуется доступ к интернету. Размерность векторов модели — **384**, это значение нужно передавать при создании коллекции.

Сервис будет доступен по адресу http://localhost:8000. Интерактивная документация Swagger — http://localhost:8000/docs.

### Способ 2: через Docker

Убедитесь, что установлен Docker (и `docker compose` для Docker Desktop / Engine).

```bash
# Собрать образ и запустить контейнер
docker compose up --build
```

Или без docker-compose, напрямую:

```bash
docker build -t fas .
docker run -p 8000:8000 \
  -e COLLECTIONS_PATH=/app/collections \
  -v "$(pwd)/collections:/app/collections" \
  fas
```

После запуска сервис будет на http://localhost:8000, документация — на http://localhost:8000/docs.

> В `docker-compose.yml` каталог `./collections` монтируется в контейнер, поэтому данные коллекций сохраняются на хосте и переживают пересоздание контейнера. Каталог `./src` также пробрасывается для удобства разработки.

### Как устроена подгрузка индекса с диска

FAISS-индекс хранится на диске в виде файла `index.faiss`. Чтение большого индекса с диска на каждый запрос дорого, поэтому реализован кэш [`IndexCache`](src/services/index_manager.py:12) — LRU-кэш размера `max_size=2`, хранящий уже загруженные объекты `faiss.Index` в памяти.

При обращении к коллекции [`IndexManager.load_index()`](src/services/index_manager.py:83):
1. Проверяет кэш.
2. Если записи нет — читает индекс с диска через `faiss.read_index()` и кладёт в кэш.
3. Последующие обращения к той же коллекции получают индекс из памяти без перечитывания диска.

### Почему нужен кэш и как обеспечивается его согласованность с диском

Кэш нужен, чтобы **не перечитывать файл индекса с диска на каждый запрос поиска и апсерта**. FAISS-индекс может занимать десятки и сотни мегабайт; десериализация — затратная операция. Держать индекс в памяти критично для производительности поиска.

Проблема кэша — риск устаревания: кто-то изменил `index.faiss` на диске, а в памяти осталась старая версия. Согласованность обеспечивается двумя механизмами:

1. **Проверка `mtime` (время модификации файла).** В кэше вместе с индексом хранится `st_mtime` файла на момент загрузки ([`IndexCache.put()`](src/services/index_manager.py:32)). При каждом запросе к кэшу ([`IndexCache.get()`](src/services/index_manager.py:19)) текущее `mtime` файла сравнивается с сохранённым; если они расходятся — запись кэша удаляется и индекс перечитывается с диска.
2. **Явная инвалидация.** После любой операции, меняющей индекс на диске (создание коллекции, добавление векторов, перестроение, удаление коллекции), соответствующая запись кэша удаляется через [`IndexCache.invalidate()`](src/services/index_manager.py:44). Так кэш не отдаёт устаревший индекс сразу после записи.

Дополнительно кэш ограничен по размеру (LRU, 2 коллекции) — при превышении вытесняется наименее используемая запись. Из-за этого компромисса при одновременной активной работе с более чем двумя коллекциями индексы будут периодически выгружаться и заново читаться с диска.

### Консистентность при записи

**SQLite — источник истины по метаданным, FAISS-индекс — производная структура.**

При upsert ([`CollectionService.upsert_points()`](src/services/collections_service.py:87)):
1. Текст эмбеддится моделью в вектор.
2. Метаданные точки записываются в SQLite (при повторном `external_id` старые версии помечаются `deleted=True`, создаётся новая запись). Это атомарная операция с транзакцией.
3. Вектор добавляется в FAISS-индекс, индекс сохраняется на диск.

Если шаг 3 падает (например, ошибка записи индекса), метаданные в SQLite уже безопасны — сервис возвращает ошибку с подсказкой выполнить перестроение индекса через `POST /collections/{name}/points/rebuild`. Это гарантирует, что **данные не теряются даже при сбое частичной записи**.

### Как реализовано удаление

Удаление выполнено как **soft-delete**:

- [`MetadataDB.delete_points()`](src/core/database.py:67) помечает точки `deleted=True` в SQLite, физически не удаляя записи. Это позволяет откатить/сохранить историю и избегает проблем с консистентностью индекса.
- **Индекс FAISS при удалении не перестраивается** — векторы удалённых точек остаются в нём. При поиске ([`CollectionService.search()`](src/services/collections_service.py:114)) результаты фильтруются: точки с флагом `deleted=True` или отсутствующие в метаданных пропускаются.

Такой подход прост и консистентен «по построению»: индекс никогда не расходится с метаданными по составу, потому что настоящим источником правды является SQLite. Плата за это — рост размера индекса и накопление «мусорных» векторов со временем. Полная очистка достигается перестроением индекса (`rebuild`), которое собирает только активные точки.

## Эндпоинты

### Коллекции

#### `POST /collections` — создать коллекцию

Тело запроса:

```json
{
  "collection_name": "documents",
  "vector_size": 384,
  "distance": "cosine",
  "index": { "type": "flat" }
}
```

`vector_size` должен совпадать с размерностью эмбеддинг-модели (**384**), иначе вернётся ошибка. `distance`: `cosine` | `dot` | `euclid`. `index.type` поддерживается `flat` (только он реализован).

Пример:

```bash
curl -X POST http://localhost:8000/collections \
  -H "Content-Type: application/json" \
  -d '{"collection_name":"documents","vector_size":384,"distance":"cosine","index":{"type":"flat"}}'
```

Ответ: `{"status": "created", "collection": "documents"}`

#### `GET /collections` — список коллекций

```bash
curl http://localhost:8000/collections
```

#### `GET /collections/{name}` — информация о коллекции

```bash
curl http://localhost:8000/collections/documents
```

Ответ:

```json
{
  "name": "documents",
  "vector_size": 384,
  "distance": "cosine",
  "points_count": 3,
  "index_type": "flat"
}
```

#### `DELETE /collections/{name}` — удалить коллекцию

```bash
curl -X DELETE http://localhost:8000/collections/documents
```

Ответ: `{"status": "deleted", "collection": "documents"}`

### Точки

#### `PUT /collections/{name}/points` — добавить или обновить точки (upsert)

Тело запроса — список точек. Текст каждой точки эмбеддится автоматически.

```json
{
  "points": [
    { "id": 1, "text": "FAISS — библиотека для эффективного поиска ближайших соседей", "payload": {"source": "wiki"} },
    { "id": 2, "text": "FastEmbed — быстрый инструмент получения эмбеддингов текста", "payload": {"source": "docs"} },
    { "id": 3, "text": "SQLite — встраиваемая реляционная база данных", "payload": {"source": "book"} }
  ]
}
```

Пример:

```bash
curl -X PUT http://localhost:8000/collections/documents/points \
  -H "Content-Type: application/json" \
  -d '{"points":[{"id":1,"text":"FAISS — библиотека для эффективного поиска ближайших соседей","payload":{"source":"wiki"}},{"id":2,"text":"FastEmbed — быстрый инструмент получения эмбеддингов текста","payload":{"source":"docs"}},{"id":3,"text":"SQLite — встраиваемая реляционная база данных","payload":{"source":"book"}}]}'
```

Ответ: `{"status": "upserted", "count": 3}`

Если точка с тем же `id` уже существует, её данные заменяются (старая версия помечается удалённой).

#### `POST /collections/{name}/points/search` — семантический поиск

Тело запроса:

```json
{
  "text": "какая база данных встроенная и реляционная?",
  "limit": 3,
  "with_payload": true
}
```

`limit` — число результатов (по умолчанию 10). `with_payload` — включать ли payload (по умолчанию `true`).

```bash
curl -X POST http://localhost:8000/collections/documents/points/search \
  -H "Content-Type: application/json" \
  -d '{"text":"какая база данных встроенная и реляционная?","limit":3,"with_payload":true}'
```

Ответ (массив, отсортирован по убыванию релевантности):

```json
[
  {
    "id": 3,
    "score": 0.712345,
    "payload": { "source": "book" }
  },
  {
    "id": 1,
    "score": 0.534211,
    "payload": { "source": "wiki" }
  }
]
```

Для метрики `cosine` score — это косинусная близость (чем больше, тем лучше); для `euclid` — евклидово расстояние (чем меньше, тем лучше).

#### `POST /collections/{name}/points/delete` — удалить точки

Тело запроса:

```json
{ "ids": [2] }
```

```bash
curl -X POST http://localhost:8000/collections/documents/points/delete \
  -H "Content-Type: application/json" \
  -d '{"ids":[2]}'
```

Ответ: `{"status": "deleted", "count": 1}`

Удаление мягкое: точка исключается из результатов поиска, но остаётся в индексе до перестроения.

#### `POST /collections/{name}/points/rebuild` — перестроить индекс

Пересобирает FAISS-индекс только из активных (не удалённых) точек метаданных. Полезен после сбоев записи или для очистки индекса от удалённых векторов.

```bash
curl -X POST http://localhost:8000/collections/documents/points/rebuild
```

Ответ: `{"status": "rebuilt", "count": 3}`

## Полный сценарий использования

Пошаговый пример «создать → загрузить → найти»:

```bash
BASE=http://localhost:8000

# 1. Создать коллекцию (flat, cosine, размерность модели 384)
curl -X POST $BASE/collections \
  -H "Content-Type: application/json" \
  -d '{"collection_name":"documents","vector_size":384,"distance":"cosine","index":{"type":"flat"}}'

# 2. Загрузить точки (текст эмбеддится автоматически)
curl -X PUT $BASE/collections/documents/points \
  -H "Content-Type: application/json" \
  -d '{"points":[
    {"id":1,"text":"FAISS — библиотека для эффективного поиска ближайших соседей","payload":{"topic":"search"}},
    {"id":2,"text":"FastEmbed — быстрый инструмент получения эмбеддингов текста","payload":{"topic":"embedding"}},
    {"id":3,"text":"SQLite — встраиваемая реляционная база данных","payload":{"topic":"database"}}
  ]}'

# 3. Выполнить семантический поиск
curl -X POST $BASE/collections/documents/points/search \
  -H "Content-Type: application/json" \
  -d '{"text":"встраиваемая база данных","limit":2,"with_payload":true}'

# (опционально) удалить точку и перестроить индекс
curl -X POST $BASE/collections/documents/points/delete \
  -H "Content-Type: application/json" \
  -d '{"ids":[2]}'
curl -X POST $BASE/collections/documents/points/rebuild
```

## Ограничения и особенности реализации

- Поддерживается только тип индекса `flat` (полный перебор). Реализованы все три метрики, но для `cosine` векторы нормализуются, а поиск идёт по внутреннему произведению.
- `vector_size` жёстко привязан к модели эмбеддинга (384). Создать коллекцию другой размерности нельзя.
- Удаление — мягкое (soft-delete): до перестроения индекса векторы удалённых точек остаются на диске и занимают место.
- Кэш индексов ограничен двумя коллекциями (LRU) — при большом числе активных коллекций будут повторные чтения индекса с диска.
- Модель эмбеддинга скачивается один раз при первом запуске; без сети сервис не стартует (эмбеддинг невозможен).

## Выводы

### Что получилось

Собран законченный вертикальный срез векторного поискового сервиса: REST API (FastAPI), эмбеддинг текста (FastEmbed), индекс (FAISS) и хранилище метаданных (SQLite) объединены в единый поток — от загрузки текста до семантического поиска. Сервис поднимается и локально, и в Docker, покрывает полный цикл работы с коллекциями: создание, наполнение, поиск, удаление, перестроение. Особое внимание уделено надёжности: SQLite выступает источником истины, а индекс всегда можно пересобрать из метаданных.

### Компромиссы при проектировании

- **Размерность векторов фиксирована моделью (384).** Это упрощает схему и гарантирует совместимость, но лишает гибкости (нельзя хранить коллекции с другой размерностью в одном сервисе).
- **Soft-delete вместо физического удаления.** Дешёво и консистентно, но ведёт к росту индекса и требует периодического `rebuild`.
- **`flat`-индекс.** Гарантирует точный поиск и прост, но не масштабируется на большие объёмы (полный перебор по всем векторам).
- **Кэш на 2 коллекции.** Экономит память, но при большем числе коллекций снижает выгоду кэширования.
- **Индекс на диске — производная структура.** Упрощает восстановление, но добавляет накладные расходы на перестроение и делает записи не полностью атомарными «за один шаг».

### Проблемы, возникшие в процессе

- **Ограничения FAISS.** `IndexIDMap2` позволяет добавлять и удалять векторы по id, но удаление не уменьшает физический размер файла индекса; перестройка обязательна для очистки. Также FAISS не предоставляет встроенного механизма фильтрации по метаданным — фильтрацию пришлось реализовывать на стороне сервиса через SQLite.
- **Неудобства FastEmbed.** Загрузка модели требует сети при первом старте; размерность модели необходимо измерять отдельно. API эмбеддинга возвращает генераторы, поэтому пришлось приводить результат к `numpy` и партиям (батчам), чтобы работать с FAISS единообразно.
- **Неполнота интерфейса.** Некоторые эндпоинты реализованы в упрощённом виде: например, обработчик параметров пути и часть обработки ошибок могли бы быть аккуратнее; это отражено в коде как точки роста.

### Узкие места текущего решения

- **Производительность:** `flat`-индекс означает линейный поиск — на миллионах точек latency растёт линейно. Нет пагинации и предварительной фильтрации.
- **Консистентность:** обновление «SQLite → индекс» не атомарно; при сбое между шагами индекс временно рассинхронизирован с метаданными до перестроения.
- **Масштабируемость:** SQLite рассчитана на однопроцессный сценарий; кэш индексов ограничен двумя коллекциями; нет горизонтального масштабирования и шардирования.
- **Память:** все индексы загружаются в RAM целиком.

### Что можно улучшить

- Добавить другие типы индексов FAISS (`IVF`, `HNSW`, `PQ`) с обучением/параметрами, чтобы ускорить поиск на больших объёмах.
- Сделать запись атомарной через стратегию журнала (WAL) или вынести индекс в отдельную очередь обновлений.
- Реализовать физическое удаление векторов (точечное) и фоновую компакцию индекса вместо полного перестроения.
- Фильтрация по payload прямо в запросе (через метаданные) без пост-фильтрации результатов.
- Заменить/дополнить SQLite Postgres для горизонтального масштабирования и конкурентного доступа.
- Увеличить размер и сделать конфигурируемым кэш индексов, добавить политику загрузки по требованию.
- Конфигурация модели эмбеддинга через переменные окружения, предзагрузка модели в образ.
- Добавить тесты и метрики (latency поиска, hit-rate кэша) и покрыть контракты API.
